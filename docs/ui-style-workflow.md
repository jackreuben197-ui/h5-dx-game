# UI 风格开发流程

本流程适用于 h5-dx-game 的 style2、style3 及后续风格。每次换肤都要同时证明设计完整、功能等价和共享逻辑可复用；不能把静态首页出图或成功构建当作换肤完成。

## 从这里开始开发新风格

本页是 DX 牌桌换肤的开发总入口。按阶段 0–5 执行，先同步本轮指定的 MX 来源分支，再根据集成后的代码整理 AI 设计要求，交给 Stitch 出稿。审稿时对照原功能和布局约束，将差异写回该风格的 DESIGN.md。用户确认设计稿后开发，最后用相同数据和操作比较两套风格，发现缺口回到阶段 3。

| 要找什么 | 去哪里 |
| --- | --- |
| 当前风格的设计要求 | [当前设计入口](../DESIGN.md)指向本轮正文。[style2 设计要求](styles/style2/DESIGN.md)含视觉方向、功能状态、布局尺寸、审稿修订和 UI 以外的改动理由。 |
| 开始写 style3 的要求 | 复制[设计约束模板](templates/DESIGN.template.md)到 `docs/styles/style3/DESIGN.md`，填写本轮来源分支、实际同步结果、视觉方向和功能对照风格。 |
| 给 AI 的参考图和审稿依据 | 从[已保存的 style1 截图](styles/style2/reference/style1/README.md)选择与本轮基线相符的场景。同步改变了画面或功能时补拍对应场景。 |
| 实现与验收示例 | 查看[双风格验收记录](styles/style2/implementation/round1/README.md)和[后续间距、遮挡与底栏复验](styles/style2/implementation/content-capacity/README.md)。 |

## 快速启动

1. 读取项目 README、当前 AGENTS.md、本流程及上一风格的验收记录。
2. 确定本轮 MX 来源仓库和分支，在 DX 完成下方阶段 0 的增量同步和验证，再确定功能对照风格、新风格目录和视觉方向。
3. 复制 `docs/templates/DESIGN.template.md` 到 `docs/styles/styleN/DESIGN.md`，填好任务参数；更新根 DESIGN.md 的链接。不要覆盖历史风格文档。
4. 从同步后的 DX 提取组件、入口、状态、布局及桥接清单，按受影响场景补拍参考图，补齐设计约束。
5. 将约束、代表性截图及分批任务交给 Google Stitch；审核后才按审定稿实现。
6. 新 UI 放入 `src/assets/styleN`，必要的通用接口或逻辑修复放回共享层。
7. 双风格执行相同数据和操作场景，记录视觉与行为证据。发现缺口先回写约束，再回到设计审核阶段修订和重验。

给后续执行者的启动指令可直接使用：

> 请读取 docs/ui-style-workflow.md，按模板建立 style3 的 DESIGN.md。先确定本轮 MX 来源分支并把上次已同步 SHA 至本轮目标 SHA 的适用更新同步进 DX，验证后记录基线和功能对照风格，再从同步后的代码提取约束，交给 Google Stitch 设计并审核。新 UI 放在 src/assets/style3；deps/h5-game 不动。按文档闭环实施，不能跳过双风格功能验收，也不能把未执行的验证标成通过。

## 固定边界与任务参数

每次填写：项目名、来源仓库、分支及完整 SHA、功能对照风格、新风格目录、视觉方向、设计工具、支持布局、目标视口、明确排除项、当前阶段。

固定边界：

- 只改牌桌及归属牌桌的 UI，不重设计 H5 大厅、登录、支付等外壳流程。混合界面的归属需逐项查代码，不能只凭截图判断。
- `deps/h5-game` 源码、配置和依赖保持不变。不通过改桥接协议或伪造接口结果来配合设计。
- 保留已有功能、数据含义、权限控制、布局设置和业务流程。不得以新风格为由隐藏现有选项。
- 新 UI 使用现有 DOM/TypeScript 技术与协议，不自行引入另一套游戏引擎、WebSocket 或业务计算。
- 先读取目标基线的实际代码和约定；组件数、目录、测试数、支持状态以本次盘点为准，不能照抄旧文档数字。

## 阶段 0 同步 MX 上游，再锁定本轮基线

1. **确定来源。** 默认同步 MX 远端的 `reorg-qa`，确认该分支不存在时自动同步 `main`。用户明确指定其他分支时，以当轮指令为准。 查询失败时先处理网络或权限问题。将实际选中的分支与提交 SHA 写入本轮 DESIGN.md。
2. **在临时目录取得增量。** DX 拥有独立提交历史。每轮在系统临时目录建立单独的 MX 仓库，从 MX 来源 URL 获取本轮分支并记录完整目标 SHA。从上次同步记录读取已处理的 MX SHA 及暂缓项。若两个 SHA 相同，记录零增量并复核暂缓项。若切换分支或发生历史改写，使用 merge-base 及两侧提交和文件差异核对，单列旧来源独有改动的去留。
3. **把选定的文件差异应用到 DX。** 只从临时 MX 仓库导出经审核的文件补丁，在 DX 工作树应用和适配。从当前 DX 工作成果开始，保护已有风格和未提交改动。按提交和路径核对共享接口、业务、style1 组件及其消费者、测试和设计约束。可直接采用的更新按原意合入，有 DX 定制的文件逐块适配。记录每项采用、适配、排除或暂缓的理由。保持 `deps/h5-game` 边界，涉及共享层的适配按本流程记录必要性、可复用性和耦合。来源仓库只读。
4. **验收并交接。** 在集成后的 DX 上运行受影响的类型、测试和现有风格场景，对照同步前的既有失败。记录 MX 旧/新 SHA、DX 集成版本、保留差异、验证结果及受影响的截图清单。涉及本轮设计的更新都已落实且验证后，才将目标 SHA 登记为本轮已同步基线，开始提取设计约束和出稿。只完成 fetch 时状态为“待集成”。若设计中途决定接收更新，重走此步并回审受影响的稿件。

### 独立历史与同步命令

DX 初始化一次，以自己的项目快照作为首个提交。后续集成在 DX 中形成普通提交，父提交来自 DX。MX 的 SHA 用于追踪来源，记录在同步单和提交说明中。不要在 DX 注册 MX 远端、fetch、pull、merge 或复制 MX 的 `.git`。DX 自己的远端单独配置。

从 DX 根目录运行下列命令。填写 MX 来源 URL 和上次已同步的完整 SHA。本轮另有指定分支时设置 `MX_BRANCH_OVERRIDE`。

```sh
set -e
DX_ROOT=$(git rev-parse --show-toplevel)
: "${MX_SOURCE_URL:?请设置 MX 来源仓库 URL}"
: "${PREVIOUS_MX_SHA:?请设置上次已同步的完整 MX SHA}"
SYNC_TMP=$(mktemp -d "${TMPDIR:-/tmp}/dx-mx-sync.XXXXXXXX")
MX_TMP="$SYNC_TMP/mx"
git init -q "$MX_TMP"
git -C "$MX_TMP" remote add origin "$MX_SOURCE_URL"
MX_BRANCH=${MX_BRANCH_OVERRIDE:-reorg-qa}
if [ "$MX_BRANCH" = reorg-qa ]; then
  if git -C "$MX_TMP" ls-remote --exit-code --heads origin refs/heads/reorg-qa >/dev/null; then
    MX_BRANCH=reorg-qa
  else
    status_code=$?
    [ "$status_code" -eq 2 ] || exit "$status_code"
    MX_BRANCH=main
  fi
fi
git -C "$MX_TMP" fetch --no-tags origin "refs/heads/$MX_BRANCH"
TARGET_MX_SHA=$(git -C "$MX_TMP" rev-parse --verify 'FETCH_HEAD^{commit}')
if ! git -C "$MX_TMP" cat-file -e "$PREVIOUS_MX_SHA^{commit}"; then
  git -C "$MX_TMP" fetch --no-tags origin "$PREVIOUS_MX_SHA"
fi
git -C "$MX_TMP" merge-base "$PREVIOUS_MX_SHA" "$TARGET_MX_SHA"
git -C "$MX_TMP" log --left-right --oneline "$PREVIOUS_MX_SHA...$TARGET_MX_SHA"
git -C "$MX_TMP" diff --name-status "$PREVIOUS_MX_SHA" "$TARGET_MX_SHA"
```

核对上面的差异清单。以下示例只同步一个已审核路径，在同一 shell 中将 `REVIEWED_PATH` 设为对应相对路径。多个关联文件可在同一条 diff 命令中逐个列出。若上次 SHA 无法从来源获取，先找回记录对应的 MX 基线再做比较。

```sh
: "${REVIEWED_PATH:?请设置已审核的 MX 文件路径}"
git -C "$MX_TMP" diff --binary "$PREVIOUS_MX_SHA" "$TARGET_MX_SHA" -- "$REVIEWED_PATH" > "$SYNC_TMP/selected.patch"
git -C "$DX_ROOT" apply --check "$SYNC_TMP/selected.patch"
git -C "$DX_ROOT" apply "$SYNC_TMP/selected.patch"
```

遇到 DX 定制导致补丁不匹配时，在临时仓库查看 MX 前后版本，逐块适配到现有 DX 文件。遇到 LFS 资源时在临时 MX 工作区检出目标版本并拉取对应 LFS 内容，核对文件哈希后拷贝实际素材，由 DX 的 LFS 规则重新登记。DX 的来源记录、配置和风格目录按需整合，`deps/h5-game` 保持冻结。验证现有风格，再记录 MX SHA 和对应 DX 版本。仅在临时目录创建 MX 对象，后续更新沿用此流程。

### 同步后的基线检查

核实目标仓库、工作区改动、本地分支与远程分支差异。新建独立项目时从确认的提交建立，不夹带来源工作区改动。无法同步远程时只记录“本地缓存候选”，不能称为远程最新基线。

记录完整 SHA、依赖锁文件、H5 跟踪文件基线及版本来源。H5 是普通跟踪目录还是子模块应实际核对，不预设。保留文件清单或哈希用于最终比较。

运行基线提供的类型检查、测试、构建和代表性浏览器场景，保存失败与已知问题。测试命令应从当前 package.json 核实；MX 候选基线包含 `npm run check`、`npm test`、`npm run build`，但后续风格必须再次确认。

通过条件：基线可复现；既有问题和新任务范围明确；未提交改动受到保护。

## 阶段 1 提取设计约束

从组件、config.json、CSS、布局实现、控制器、数据绑定、协议处理及测试场景提取以下清单：

- 所有牌桌区域、操作入口、弹窗和特殊玩法界面；每项标注代码归属。
- 显示条件、可用/禁用条件、用户动作、业务结果、加载/失败/关闭状态。
- 空座、本人/他人、观战、行动、弃牌、全下、结算、切桌、重连等实际支持状态。
- 座位数、布局选项、手牌数、单/双公共牌、底池/边池、长金额、多语言、网络头像。
- 设计尺寸、组件局部坐标与锚点、层级、点击区域、遮罩与穿透、安全区、短屏与滚动。
- 资源尺寸、透明度、九宫格/拉伸策略、字体、动效及减少动效的处理方式。

使用稳定需求编号关联“代码 → 场景 → 设计稿 → 实现 → 验收”。所有未知项明确标记待核实，不把猜测交给设计工具当事实。

通过条件：核心玩法和全部现有入口有归属；关键状态有输入与预期；设计工具知道哪些可改变、哪些必须保持。

## 阶段 2 设计工具出稿

先验证 Google Stitch 的访问、登录、素材导入与导出能力；如果受阻，记录具体阻塞，不虚构已交付设计或擅自换工具。

每批输入包括：设计约束版本、需求编号、真实截图、示例数据、允许改动范围及交付清单。不要上传账号、token 或其他秘密。

建议三批：

1. 主牌桌和视觉规范：桌布、座位、手牌、公共牌、筹码、底池、行动按钮。
2. 关键状态与适配：加注展开、自动操作、满座、双公共牌、结算、长文案和短屏。
3. 完整桌内面板：设置、带入、战绩、牌谱、聊天、保险和基线已支持的特殊玩法。

要求保留功能语义，不新增没有后端支持的操作。素材、字号、间距、交互状态和响应式规则必须足够明确；仅有一张主界面图不算整套设计。导出代码只作参考，不取代项目架构。

记录每批提示词、稿件链接/文件、版本和对应约束版本，保证下一次迭代可复现。

## 阶段 3 审稿并更新 DESIGN.md

逐项比较基线功能、约束与稿件，分类记录视觉偏差、功能遗漏和实现不可行项。核查不能只看正常状态，还要看长内容、禁用、错误、弹窗打开和特殊玩法。

差异表包含：编号、关联需求、问题、影响、修订要求、责任层、状态和复验方式。先补约束，再补稿；不允许为了通过验收删掉原本必须保留的功能。已接受的视觉差异与业务语义分别记录。

通过条件：该批次没有未解决的功能阻塞，稿件能实现，关键状态及适配规则齐备。可按已审定组件分批开发，未审定部分不能标记完成。

## 用户审稿与实现授权

每次任务记录是否要求用户审稿。style2 当前已明确要求：完成设计审核后展示稿件并暂停，得到用户确认后才能进入实现。后续任务继承用户仍有效的要求，不以等待时长代替确认。若没有此要求且用户已授权端到端开发，不额外添加审批门槛。

## 阶段 4 实现新风格并修复耦合

参照 style1 的目录组织：入口、StyleClient、table/components、table/layouts、appearance、resources、effects、audio、build。代码和素材分开；新组件资源 paths 指向本风格 resources 下的真实相对路径，遵循基线开发态原图、构建态打包的规则。

改动位置遵循：

| 原因 | 位置与处理 |
| --- | --- |
| 颜色、素材、布局、组件表现 | 新风格目录 |
| 选择风格、外观选项、构建资源 | 现有装配入口和构建包装，属于正常接入 |
| 业务层依赖 style1、视图内藏业务计算、跨组件 DOM 耦合 | 修正共享接口/逻辑边界，双风格共同回归 |
| H5 外壳行为 | 保留现有协议，本任务不修改 H5 |

不得在新风格复制一套下注、金额换算、权限判断或协议处理。共享层不反向导入具体风格。组件内部布局采用局部坐标；父组件放置整个组件，跨组件动画通过显式坐标转换适配。

保留原有定向数据绑定与生命周期。切桌、重连、离桌和销毁时清理监听、计时器、动画及过期异步结果。CSS、资源和构建选择不能串到另一风格。资源/Spine等专用能力不因换肤而强制抽象成万能配置系统。

每次 UI 层以外的修改必须逐项记录：是否必须修改、只改 UI 的替代方案、能否供多个 style 共用、是否原本耦合了 UI、最小修正及两套风格的回归证据。正常装配与耦合修复分开记录。不要顺带重写无关架构。

## 阶段 5 双风格验收

### 设计符合度

使用相同视口、缩放、语言、数据和稳定动画时点，比较新风格截图与审定稿。逐项验证布局、素材、字号、颜色、交互状态、适配和动效。不使用覆盖所有场景的单一像素阈值；按组件记录可接受误差及原因。原设计有意的重叠应单独标注。

### 功能等价性

对照风格与新风格使用同样初始快照、协议事件及操作序列。比较可执行动作、请求参数、状态迁移、金额、权限与最终结果，而非只比较 DOM 外观。动效可以不同，触发条件及完成后的业务状态必须一致。

覆盖全部入口和关键状态。按风险选择座位数、布局、视口、语言、身份和玩法组合；下注/加注、自动操作、手牌选择、双公共牌、特殊玩法、切桌、重连及清理优先。既有测试依赖 style1 路径时要检查可复用性，不能只改测试名称就声称覆盖新风格。

证据分层记录：类型/单测、离线浏览器、真实 H5 联调、真实服务端、实体设备。离线协议模拟和桌面移动模拟不能冒充实服或真机验收。

### 闭环

发现遗漏 → 补充 DESIGN.md 的需求和场景 → 回到阶段 3 审核 → 必要时回到阶段 2 补稿 → 阶段 4 修正 → 阶段 5 重验。

纯实现偏差也经过阶段 3 判断，但不必强迫设计工具改一张本来正确的稿。文档规则若已完整，记录关联需求与回归案例即可，不反复复制规则。共享层变动复验两套风格，视觉局部变动做对应影响范围验证。

## 完成门槛与交付

- 需求追踪表无遗漏功能，所有必须项有通过证据；未执行、受阻、不适用和已接受差异分别记录。
- 新风格符合审定稿；对照风格无新增回归；既有基线缺陷没有被悄悄改写成通过。
- 类型检查、必要测试、开发态资源、生产构建和真实入口加载完成验证。
- deps/h5-game 与冻结基线一致，原项目工作区不被修改。
- 保留可访问的设计稿、提示词、版本、素材来源、验收记录及复现步骤；截图不随意纳入 Git，遵守目标仓库规则。
- 未完成项不记为通过。交付范围若受条件限制，明确剩余项和影响，不宣称全量验收完成。

交付包括新风格代码、共享层必要修正、DESIGN.md、设计稿和素材、验收报告。发布、推送等按用户实际授权执行，不把文档中的流程说明当作发布授权。

## 跨风格参考截图复用

用户要求把本次截图保存为 style3 可直接复用的基点。每次风格目录使用 reference/<来源风格>/ 保存原始参考，manifest 记录提交 SHA、场景、布局、视口、语言、数据类型、实际时间和文件哈希。设计稿和实现截图分目录保存，不覆盖来源截图。

优先复用已有基线。只有来源代码、功能或布局发生改变时补拍受影响场景。持久基点不要只放临时目录或被忽略的 docs/qa；截图随项目保留并按 LFS 规则提交。尚未采集的清单保留 pending，不能虚构文件或时间。

## Stitch 操作与设计存档经验（style2）

- 连接能列出标签页不等于能读取/操作页面；记录具体失败环节，不凭超时判断是权限拒绝。正常Chrome重启曾恢复DOM读写，复杂画布时可用原生AX继续。
- 文件chooser事件超时但系统文件窗口已打开时，可通过正常文件选择窗口上传；成功证据是项目对话列出附件。不要重复要求登录或复制浏览器凭据。
- 导出前核对选中的节点：导入的参考图也是canvas节点，Select All可能只选中当时已有节点。生成结束后明确选择生成稿标题，确认上下文路径为screens/*.html或规范文档，再导出ZIP。
- ZIP实际可能仅含HTML、没有PNG。保留原始ZIP/HTML，再用已授权的本地浏览器按稿件尺寸渲染截图；外部字体/示例头像加载情况和失败数写入记录，不将渲染图冒称Stitch原生PNG。
- macOS保存窗口的文件名输入框不能用绝对路径代替选择目录，否则斜杠可能转成冒号。用“前往文件夹”选中项目设计目录，再填纯文件名；最后从文件系统验证内容。
- 设计稿HTML只能放docs/styles/styleN/design/roundN，不直接复制进生产风格。每轮保留提示词、修订意见、稿件、截图、manifest与审核结论。

## 主桌先行与视觉审核门槛（R2用户反馈后补充）

不要在主桌构图尚未获认可时批量扩展十多张界面。先提交主桌标准屏+长屏及小型组件规范，检查满屏、座位沿全高分布、可读字号和插画一致性；用户要求先审稿时展示该方向并暂停。主桌通过后再扩状态与弹窗，避免把相同缺陷批量复制。

设计验收不能只清点节点数和图片是否加载成功。必须从实际导出HTML/画面检查：

1. 标注尺寸=真实viewport=导出图片尺寸；底栏贴底，背景覆盖全部高度，长屏增加的空间由布局分配，不产生尾部空白。
2. 玩家姓名、余额、下注、背牌和头像分别检查边界；公共牌对侧边下注、本人头像对聊天/加时、行动按钮对手牌做有针对性的矩形相交检查，之后人工看图复核。
3. 不用普通UI图标/emoji充当“卡通可爱”完成，查看图标在实际24–36px下是否仍有统一轮廓、描边、配色与语义。桌面轮廓、图标和头像框共同构成风格。
4. 保留首轮失败证据和用户否决原因；未通过稿只能作为历史参考，不能继续在文档中称审定稿。不得将“已生成”或“无资源加载错误”写作视觉质量验收通过。


### 多容量底栏必须在主桌阶段审核

先从原代码提取导航分支，不只照普通桌截图。style2证据为NavigationView的3/4/6按钮分支。style3复用流程时重新核实基线，设计普通/语音/视频完整主桌；把认证标识、安全区和独立聊天入口计入容量。先按最多按钮分配宽度、热区及底栏高度，再向上排手牌、快捷与行动区。设计矩阵加入本人行动+五快捷、加注展开、0/34px安全区、320/375/440宽；不以静态三按钮概念图替代验证。窄屏底栏局部图只证明局部容量，不代表全桌响应式验收。


### 用户审阅稿必须准确对应

每次反馈须明确用户正在查看的文件与版本。文档、Stitch静态稿、imagegen美术参考分别追踪修订状态；修改另一份稿不能记为当前图已修复。展示前直接检查当前交付图的对应入口是否出现，保存原图、修订图、工具来源和完整提示词；不得用概念图的入口存在替代实际热区与功能验收。


## style3复用style2代码验收经验

- 使用MountOptions.skin按实例选择风格，产品默认只在config/UiConfig.ts装配；公共入口从config转导出，业务层不可直接导入assets/styleN。
- 优先复用现有组件的动作/生命周期契约，明确记录复用DOM的耦合。不要把一套覆盖CSS描述成结构完全独立，也不要为换美术重写业务。
- tests/fixtures/verify-style-parity.cjs比较全场景结构，verify-style-behavior.cjs比较实际动作后的金额/状态，二者不能互相替代。style2专项交互与边界脚本可复制并换新风格名；运行参数和输出约定见本轮验收README。
- 本轮发现的通用几何陷阱：桌面可滚动窗口的高度不等于固定行动区可用高度，应从root与导航测量；小屏需要显式滚动策略，不用无限缩小文字替代设计。加入滚动前/后截图和固定导航位置检查。
- 安全区测试要叠加最多导航、五快捷、本人行动和多手牌；通过标准屏不等于极短屏通过。实际浏览器、模拟34px、实体设备分别记录。
- 保存美术源提示词、独立图集、资产manifest与验收截图；原参考不可覆盖。下一风格先比来源提交，只有功能或布局变化才补拍style1基点。


生产入口必须单独验收：离线fixture显式指定layout会掩盖产品默认值。style2发现设置层曾固定original，现通过UiBrand.defaultLayout与可选设置构造参数注入，保留已有用户选择。style3应同时测全新用户、已保存旧布局、宿主入口、生产资源和匿名独立挂载，不能只验证手工配置的工作台。


### 实现反馈后的容量回归（style2补充，style3复用）

- 风格坐标缩放后再测昵称/余额间距；局部CSS数值不等于屏幕像素。完整身份牌包括姓名、余额和可能的赢家状态，不能只量头像。
- 以实际导航3/4/6分支验证同排认证、至少44px热区和安全区。style2最新用户选择为64px单排底栏加安全区，旧稿认证独占一行已被否决；新风格先确认设计约束，不因logo变大擅自增加底栏高度。
- 同时测上一玩家投注/下一玩家动作、本人余额/快捷、加入游戏/手牌、边池/公共牌、双公共牌/房间说明，避免修一处挤另一处。边池从左到右，即使只有一项也不居中。
- 长信息先保证完整行与滚动可达；长金额不能裁切。保留标准、紧凑、极短滚动、安全区及横屏截图，再人工检查实际观感。
- 专项脚本verify-style2-capacity.cjs与verify-style2-footer.cjs提供容量/相交/间距证据；交互与生产脚本支持MX_OUTPUT_DIR保存新轮次，避免覆盖旧报告。首轮误写回R1的交互报告需明确注明重跑时间，不能把其当作冻结截图基线。
